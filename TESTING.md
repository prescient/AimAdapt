# Testing strategy

AimAdapt turns files it doesn't control (KovaaK's stats CSVs) into numbers people use to judge their own progress. Two kinds of failure matter most:

1. **Wrong numbers that look right.** A miscounted session or a mis-parsed score silently misleads you. This is the biggest risk.
2. **Breaking on new input.** A game update changes the file format, or a file is caught half-written.

UI glitches matter less: they're visible, and easy to spot and fix.

So most testing effort goes into `aimadapt-core`, where all parsing and maths lives, and the UI is kept thin.

The built-in trainer follows the same pattern. All game rules live in `aimadapt-sim`, which has no graphics and is tested directly. `aimadapt-engine` only feeds it mouse input and draws what it reports.

## What runs when

| When | What | How |
|---|---|---|
| Every commit (pre-commit hook) | Formatting, clippy (warnings are errors), all tests, release build to `dist/AimAdapt.exe` | `.githooks/pre-commit`. Enable once per clone with `git config core.hooksPath .githooks` |
| Every push / PR | The same checks on a clean Windows machine, plus the exe uploaded as a build artifact | `.github/workflows/ci.yml` |
| Version tag (`v0.1.0`) | Windows installers (MSI + NSIS) attached to a GitHub release | `.github/workflows/release.yml` |
| Before a release | Real-data check and manual smoke test (below) | By hand |

## Test layers

### 1. Unit tests (in each module, `#[cfg(test)]`)

These cover pure logic with small, hand-built inputs, one behaviour per test. Today there are 17:

- **parse:** file names with ` - ` in the scenario, rejecting other files, runs crossing midnight, unknown and bad fields.
- **training:** session splitting, the 4 AM day boundary, per-scenario restart detection, streaks and goals, weekday averages, pause subtraction.
- **progress:** cm/360, improvement and best-score counting, plateaus, cold starts, restarted runs excluded, fatigue buckets.
- **discover:** Steam `libraryfolders.vdf` parsing.

**Rule:** every bug fix starts with a failing unit test.

### 1b. Trainer rules (`aimadapt-sim`)

These tests cover the scenario format, simulation, adaptive ratings, telemetry, workouts, programs, settings, profiles and imported worlds (walls and bot movement, below). Each one steps the simulation at 240 Hz with scripted aim, so no window is needed:

- **Format:** an empty file gives the defaults, TOML round-trips, unknown fields are rejected, bad values get plain messages, and the fingerprint ignores the description but not the difficulty and keeps a pinned value (a change restarts every rating). Regression tests: adaptive easy and hard are compared after the defaults fill in, targets must fit between floor and ceiling, adaptive target speed needs moving targets, and `inf` and `nan` are refused anywhere in a scenario (each of these crashed the trainer or made scores NaN). Every value the editor offers loads, and every built-in stays inside the editor's limits (built-ins used a health of 1,000,000 the editor didn't allow).
- **Field list:** every scenario field is described exactly once, every choice parses, every default is within its limits, and SCENARIOS.md mentions every field.
- **Simulation:** sphere, capsule and box hits (a box's faces, edges and corners, where a capsule of the same size misses; entering through a side face; origin inside; behind), a box that is too flat or taller than the room is refused, countdown blocks shots, kills respawn in the same frame, misses, fire rate on hold (the same at 30, 60 and 144 FPS as at 240, with no burst banked while the trigger is up: it used to depend on frame rate), a target taller than the room placed without a panic, adaptive runs starting a rotation on its first bot, time and kill limits, 60 Hz beam accuracy, bots with heads (plan K9, below), moving targets staying inside their area at a fixed distance, lifetime timeouts and shrinking, spawn spacing, time to kill not counting time spent on other targets, and the same seed replaying the same run. Every built-in scenario, in both modes, is played for 60 s and checked every frame for targets leaving the room.
- **Library:** built-ins are valid, every file in `scenarios/`, `workouts/` and `programs/` is in its hand-written table once with its own text, built-in names differ, and user scenarios save, load, rename on clash, delete, and reject `../` ids. Saves replace the file in one step and leave no temporary file.
- **Settings:** crosshair numbers are checked (`nan` loaded and drew nothing), and a profile file whose active profile is missing loads on its first.
- **Core's copies:** aimadapt-core keeps copies of the sim's lapse rate, sample rate, sub-skills and knobs; a test in aimadapt-engine, which has both crates, checks they match. It also checks that core's and the sim's formulas for the goal rate's point on the curve agree.
- **Adaptive ratings:** simulated players with a known 85% speed (0.35–1.6 s) are found within 25% after 25 targets and within 10% after 100, even from a wrong first guess. Each mix keeps success in its band: Steady 82–92%, Balanced 78–90%, Push 72–86%. A surprising result moves the rating more than an expected one: hitting a stretch target vs. one at your level, and missing one at your level vs. a stretch. Time away widens the uncertainty. In the simulation, perfect play gets faster and idling slower. Spraying clicks doesn't count as success, and tracking rates target speed with one outcome per 2 s segment. A simulated player of fixed skill plays chains of 30 runs, each started from the last one's rating: the rating must move less than 3.4% from run to run on average (it measures about 2.2%, and about 4.5% before the slope's uncertainty was carried between runs). When that player improves by 10%, more than 70% of the step must show within five runs. The chance of success at the rating is the goal rate with slips counted (`the_rating_is_hit_at_the_goal_rate_slips_included`). A run starts within 0.3% of the rating the last one ended on (`the_next_run_starts_at_the_last_rating`). A finished run keeps a curve that goes through its rating (`a_run_keeps_a_curve_through_its_rating`). The Insights chart's 85% mark equals the rating (`the_charts_85_mark_is_the_rating`). An engine test saves a bot run to a database and reads it back (`a_saved_rating_is_where_the_next_run_starts`): the next run starts at the saved rating, and the 85% mark of that scenario's Insights chart is within 0.1% of it.
- **Runs, not targets:** with no earlier rating a run is a calibration run; with one, every target (or tracking segment) in the run gets the same value, and the rating still takes the run in. A run after a long break is a calibration run again: the rule is tested on both sides of each limit (three days, and an uncertainty of 0.12), a ten-day break gives a calibration run that starts near the old rating, keeps the old best and sets no breakthrough, and a one-day gap still plays at one value. Run picks follow the mix (Balanced within 4 points of 65/20/15), stretch runs are harder and easy runs easier, and there's no stretch run after a stretch run or a run more than 10 points below the goal. Inside a block of runs the kind is planned by a pure function (`planned_kind`), tested for every mix and block length from 2 to 60: the first run is at your level, no stretch run is last or beside another, easy runs close the block, and the counts are the mix's shares rounded. A planned run plays inside its kind's band, a run outside a block draws as before, and a sim test checks that five Balanced runs go at your level, at your level, stretch, at your level, easy. A breakthrough needs the goal held at a value past your best, and is announced on the run's last step. Holding the goal takes at least 10 outcomes, and a run under 30 targets (a tracking segment counts as three) has to beat the goal by a margin: 9 of 10 doesn't hold 85%, 10 of 10 and 19 of 20 do, and 26 of 30 does. A short lucky run sets no best held, and the results screen has its own line for a run at the goal that was too short to count. A run is judged against the chance it was planned at by a pure function (`judge_against_plan`): the tolerance has a five-point floor for long runs and widens for short ones, and the cases at, above and below plan, on both sides of the edge, and with no evidence are tested. The summary carries the evidence in target-equivalents, and `aimadapt-engine` tests the HUD and results wording for each kind of run, including that a stretch run at 58% against a plan of 60% reads as planned, with no mention of the goal, and that the live rate sits beside the plan on stretch and easy runs.
- **Movement:** with acceleration, velocity never changes faster than the limit allows and strafes slow through each reversal; forward/back movement stays inside the spawn distance range and keeps sideways speed in m/s; jumps reach their height with the set airtime; regen waits for its delay; and new fields at their "off" value leave existing scenarios' fingerprints (and ratings) unchanged.
- **Regen smoothness:** on a target needing 1.5 s of beam with fast regen, steady tracking finishes every target in time and a player who slips off for 0.3 s every 1.2 s finishes none.
- **Variants:** every sub-skill has at least two built-ins; each workout variant is a real built-in with the same sub-skill as the scenario it stands in for; items alternate by week with the same number of reps; weak-spots days rotate too.
- **Hitscan target speed:** each target gets its own speed and keeps it through reversals, perfect play raises the rating and idling lowers it, and validation requires a lifetime (for target size too).
- **Knobs that fit the drill:** Static Grid, Timed Grid and Wide Flicks are rated on kill pace (a clicker inside the pace succeeds every time, one at 1.7× never does; Timed Grid keeps its 2 s timers), and a kill after two misses doesn't count while one miss is allowed. Micro Flicks and Precise Track are rated on size: every target in a run has the run's size, Micro Flicks keeps its 1.5 s lifetime and Precise Track its slow speed, quick hits succeed and timeouts fail, and calibration shrinks the ball for a steady tracker. Strafe Clicks is rated on target speed with a fixed lifetime.
- **Curve movement:** on Control Track the heading never turns faster than the turn rate between frames (bounces aside), speed stays within 8%, and the target turns through more than a full circle in 20 s. Curve movement without a turn rate is rejected.
- **Switching:** Speed Switch has no target timers and is rated on kill pace: kills comfortably inside the pace all count, a player at 1.7× the pace gets one failure per empty window and none of the late kills, and calibration finds a 0.7 s player. Stability Switch sweeps at least 15° per direction on targets at most 3.5° across, and counts only engaged time, so a player who looks away 0.6 s after every kill still scores above 97% (below 85% with the old scoring), and a half-damaged target that's abandoned stays engaged for exactly its heal time.
- **Telemetry:** reaction, time to reach, overshoot and corrections for a scripted flick. Shots past the target read as positive "along", and aiming behind a strafing target reads as negative lead.
- **Workouts and settings:** built-in workouts only use real scenarios, steps expand in order, display settings round-trip, and the play area is centered and clamped, and can sit at the top, bottom or any position (out-of-range positions are rejected). A 24" area on a 42" 4K screen comes out at 2194x1234.
- **Profiles:** game sensitivities convert to the known cm/360 (Overwatch 5.3 at 400 DPI is 65.35, Valorant 0.35 at 800 is 46.65, CS2 1.0 at 800 is 51.95). Profiles round-trip, bad ones are explained, and old single-settings files become a Default profile. The engine tests saving profiles and loading the active one or one by name.
- **Training settings:** `aimadapt-sim` checks that a saved goal and mix load back, that a missing or damaged `training.toml` gives the defaults, that a goal outside 1 to 600 minutes (zero, negative, over 600, not a number) is refused with nothing written, and that a file with a bad goal keeps its mix. The engine checks that a chosen mix is used for every profile and that, until one is chosen, each profile's own mix carries over. The app starts with the saved goal and the sim and core agree on the default one, and the CLI's `time` uses the saved goal unless `--goal` is given.
- **Programs:** every Core Week day is 25–33 minutes, with at most 6 drills of 3+ reps (warm-ups aside). Sunday is rest, weak-spots days put the skills most in need first (least trained, then least improved), and every sub-skill has a drill tagged with it. The engine resolves each day and builds Saturday from an empty profile. In `aimadapt-core`, the skill profile counts faster lifetimes and higher speeds as gains. The week grid marks days done, today, upcoming and rest, and compares with last week; rep and carry-over gains, the streak, and training days starting at 4 AM are checked on hand-built data. Every change carries a likely range built from the ratings' stored ranges (from the stored sd, or from the range ends when there is none), a change with zero inside its range is flagged as noise, and runs with no range give none; a least improved skill is named only once two skills have three sessions each, and a drill's carry-over only after three sessions of the drill.
- **Insights** (`aimadapt-core`): synthetic runs with a known weak direction, overshooting, low shots, tracking lag and a 200 ms recovery after direction changes produce those exact figures and coaching notes. Centering is the median distance from center over on-target samples only. On a lifetime rating that went from 0.80 to 0.62 s with a 0.22 s median reaction, the reaction note says the part you control is 0.40 s, down 31% against the rating's 23%.
- **Planned against actual** (`aimadapt-core`, plan A6): with made-up runs, a kind with no runs has a row and no figures, a long run weighs more than a short one, a gap inside the noise is "as planned" and one outside is above or below (with five points of slack on a very long run), a planned run without its length is counted apart, calibration and standard runs are ignored, and one scenario can be picked. A database-backed test saves runs and reads them back by kind and scenario. The run list's breakthroughs are derived from the history: the first held run of a version is not one, a harder one later is, an easier or equal one is not, another version's best and a calibration run's value don't count, and for tracking a higher speed is harder. `aimadapt-engine` checks that core's copy of the tolerance equals the sim's over a grid, and that a saved adaptive run carries its length. `aimadapt-cli` tests the `plan-check` text, and the UI checks that the runs table has the Kind column and Breakthrough tag and that both pages draw the shared card.
- **Insights for switching:** acquisition (kill to reaching the next target), on-target share while engaged and kills a minute come out exactly on a synthetic run, and old single-target "fastest hit" values aren't used as the best held.
- **Scenario versions** (`aimadapt-core`): a history with two fingerprints of one scenario checks that bests, notes, skill gains, carry-over and the week's comparison use only the current version, and that runs with no fingerprint count as one version. A UI check keeps the scenario page's rating figures and chart on those same runs.
- **HUD wording** (`aimadapt-engine`): size ratings on tracking show time on target, on clicking a hit rate.
- **Mouse lock** (`aimadapt-engine`): the cursor locks on start, releases when focus moves away, and locks again when focus comes back, on every click, and within half a second while focused, even when the game thinks it's already locked (after a quick alt-tab Windows drops the lock without the game noticing).
- **Results screen** (`aimadapt-core`, `aimadapt-engine`, `aimadapt-app`): the chart's points are the last ten, with this run last, from one version and one knob, ratings or scores; the note is never the rating and is the first one a player can change; the dots sit with the newest at the right and the best at the top, whether a rating or a score; the key hints for one run, a workout and the app waiting; the workout's list has one line for each scenario (a 23-run day used to run off the window) and counts the scenarios past twelve; the chart and the note give way when the window is too short for them; the line that tells the app what to open reads back, and the app keeps it out of its error lines; and the game's text is ASCII. The drawing itself is checked by eye from the smoke test's `results.png`.
- **Session summary** (`aimadapt-core`, `aimadapt-app`): the session is the one with the latest trainer run, with KovaaK's runs in the sitting counted toward its length only; a rating is compared with the last one before the session, and the change and its range come from both ratings (none without a stored range); a first session has no change; another version or another knob is never the before; breakthroughs count the session's runs only; a standard run shows the best score; a program drill is also compared with the same day of the program before, unless that run is the before; scenarios stay in the order first played; the note comes from the most played scenarios; the count of runs a trainer visit saved (and that a crash still reports it); and that the UI opens the summary only after its data is reloaded and not over a page the player asked for, an error or the editors. The page itself is checked by eye in the browser preview.
- **Strafe width:** drills with gradual turns (Hop Strafe Track, Unbroken Strafes, Hop Clicks) sweep at least as wide per strafe as their plain versions (Strafe Track, Timed Strafe Clicks), and Hop Switch at least 12°.
- **Bars and colors** (`aimadapt-engine`): bars start above the top of a capsule or box, not inside it; timed targets get a time-left bar that empties, untimed ones none; timed targets change color by wave (Timed Grid's first three share a color, the next three take the other) and untimed ones keep one; switching targets show health.
- **User guide** (`aimadapt-app`): the guide names this version, has a What's new section and a section for every page and sidebar entry, every internal link goes to a section, and it has a row for every built-in scenario, every rating and every trainer key, and an entry for every built-in workout.
- **UI start-up** (`aimadapt-app`): app.js waits for DOMContentLoaded before its first render, so views from later scripts are defined (opening on #help used to stay on "Loading").
- **KovaaK's files on Browse** (`aimadapt-app`): `sce_entries` lists each name once (the first file wins), reads tags and aim type, and marks which files the trainer can play, on the made-up fixtures.
- **Test databases only** (`aimadapt-app`, `aimadapt-engine`): `--dump-snapshot` and `--smoke` refuse to run without `--db`.
- **Ratings per scenario version** (`aimadapt-engine`): a rating carries over to the same scenario and to one with a new description, but not to one with different settings.
- **Engine record** (`aimadapt-engine`): an engine run saved through `insert_runs` gets the right score, accuracy, length and `source`, keeps separate bests for variants, and is ignored when matching KovaaK's settings.

**Engine record** also has an end-to-end test: two adaptive runs and a standard one are saved through `record::save`. The first adaptive run must be a calibration run that sets no best. The second, a day later, must start from the first's rating with the day counted (a rating read back ten days later must ask for calibration, and one read a day later must not), play at one value, and store its value and pick for the next run's guard rails, the names must keep both modes apart, telemetry, traces and replay frames must be stored, a replay must load with frames, trace and shots, and Insights must read all three back.

**Engine smoke test:** `aimadapt-engine <scenario> --smoke <folder> --db <file>` (or `--workout <id>`) has a bot that plays like a person go through short runs, then saves screenshots mid-run and on each results screen. It needs a GPU, so it's run by hand, not on CI. Check the screenshots and that the runs, with telemetry, are in the test database. Opening the app with `--db <that file>` previews Insights on bot data. Add `--handoff` to see the results screen as the app's players do, with the V and I keys.

### 2. Fixture tests (`crates/aimadapt-core/tests/`)

These run the real pipeline (file → parse → SQLite → reports) on real KovaaK's files in `tests/fixtures/`. They use 3 fixtures: a clicking run, a tracking run and a 1-second run. Unit tests in aimadapt-core also cover a run that starts and ends in the same clock second (it came out a day long), the flick chart keeping the newest 400 flicks (it kept the oldest), a trainer run saved whole or not at all, a database from a newer version being refused, and every query the app and trainer use running on the current schema (SQL stays in aimadapt-core; tests reach the connection with the `test-util` feature). Replays (`aimadapt-core`): a scenario keeps the replays of its latest 50 runs and its best (the first to reach a tied top score; for adaptive runs the best rating for the knob, so the shortest lifetime; and the best on each version), other scenarios keep theirs, and pruned runs keep their targets, shots and insights with the Replay link hidden. Regression tests: insights notes compare ratings of one knob, a tied best is the first run to reach it, the same cm/360 in other units is one sensitivity period, programs use the day-start setting, the best rating is per scenario version, and aim traces pack to 6 bytes a sample and round-trip (older traces still unpack). `insights_load_time` (ignored, run by hand in release) times a scenario's insights over 200 one-minute tracking runs.

**Fixture policy:** whenever a file breaks parsing or gives odd numbers, copy it into `tests/fixtures` and add a test before fixing it. Files still needed:

- [ ] A run with a pause (also settles the units of `Pause Duration`)
- [ ] A run that crosses midnight
- [ ] A run from an older game version, if one turns up
- [ ] A scenario name with a comma or non-ASCII characters
- [ ] A different sensitivity scale (Valorant/CS), to confirm KovaaK's scale names for cm/360
- [ ] A half-written or truncated file (see Known risks)

### 2b. Scenario file tests (`crates/aimadapt-sce`)

The `.sce` reader and converter have unit tests and fixture tests:
- **Settings:** sections and the map split, a byte-order mark, keys in any case (last one wins), positional lists with empty slots, and `X= Y= Z=` vectors. `nan` and `inf` aren't numbers (regression test).
- **Maps:** Reflex brushes (with each face's material) and spawns (`teamA` and `TeamA`), faces that point at missing vertices, and JSON primitives (with their names, such as `Clip`), procedural triangles, spawn points and volumes, waypoints and props. Errors name the line or object.
- **Shapes:** every editor primitive besides `Cube` fills its 100-unit box: round ones stand on their location centered on it sideways, angular ones start at a corner (a `DoubleRamp` is centered on its peak). Ramps slope across from their corner, `Concave` and `RampConcave` curve around their far corner and `RampConvex` around its near one, and the shapes maps pin down are solid while the rest aren't.
- **References:** bots through `.bot` and `.rot` (with weights), characters, dodge profiles and abilities, and each missing name listed once.
- **Inventory:** what counts as covered by the plan and what's a gap. Plan K7: a bot with a weapon that is told not to aim (`NoAiming=true`) is no gap, with the weapon on the bot or on its character, while the same bot aiming or saying nothing about aiming is "bots shoot back"; `InvinciblePlayer=true` on the player's character is no gap, a bot that fires with only that switch on is still "bots shoot back", and `InvincibleBots=true` there is "per-character invincibility" with the setting named.
- **Converter:** Unreal axes and units to the sim's, team masks, colors, `Cube` brushes (100 units per scale step from a corner) and rotations. Bots on a spawn volume appear anywhere in its box, which is placed like a `Cube` (regression test: they all appeared at its corner, on top of each other). Hitbox shapes (plan K5): a cuboid with a height of at least twice its radius converts to a box, a cylinder to a capsule with no note, and a spheroid stays a ball; flat cylinders and cuboids are refused, and so are cuboids when the player starts turned off the map's axes (45 degrees refused, 90 and 0 played). Spawn offsets (`convert/offsets.rs`; regression test: they turned with their spawn point, though KovaaK's runs them along the map's axes): the target lands 3 m to the map's right on a point turned 90 degrees and stays level on one pitched 30; the world keeps `offset_axes` only where the point's own axes would move a target (not for a half turn with mirrored offsets, not for a turned player with a point turned the same way, yes for a turned player with another point, and for a kind with offsets only where its points are turned); a file with no offsets stores exactly `[0.0, 0.0, -0.0]` at every version, sign included; a `GameVersion` below 2.0.5.0 turns the offsets a quarter (the version reader has its own table); the older keys are a fixed offset, a millimeter of them is nothing, and older keys with newer ones are refused naming the character; the box comparison has unit tests (same frame, half turn mirrored and not, quarter turn on one axis, a turn about the only offset's axis, zero offsets, a millimeter's tolerance); a helper's offset runs along the map's axes and its facing along its spawn point. The player's own offsets (regression tests: the older keys weren't read for the player's character): `the_players_older_offset_keys_move_the_eye` (3 m up, right and forward at 3.9.13, at 2.0.5.0 and with no version, and at 2.0.4.9 Y moves the eye back and X to the right, as measured in KovaaK's), `the_players_older_offset_runs_along_the_maps_axes` (a start turned 90 degrees, by inference), `a_tiny_older_offset_on_the_player_is_no_offset` (below 0.1 of a unit nothing moves, to the last bit), `the_players_older_offsets_that_werent_measured_are_refused` (older keys with newer ones that aren't zero, and a vertical older offset on a player that falls, each naming the character, while a flyer's, a floating player's and a falling player's sideways offset play) and `the_players_newer_offset_keys_are_the_middle_of_their_range` (to the last bit, since the eye is in the fingerprint, and turned a quarter in an old file by inference). Where a small player stands (regression tests: a body shorter than its step-up reach stayed in the air just above a floor, or was stood inside a thick one): `a_speck_of_a_player_just_above_a_floor_stands_on_it` in the importer, and in `aimadapt-sim`'s `collide.rs` `a_body_shorter_than_its_reach_still_finds_the_floor_below_it` (a 1 cm ball with no step-up, a 5 cm ball and a short capsule with a step-up, a floor past the reach and a place past the floor's edge) and `a_small_body_stands_on_top_of_a_thick_floor` (a 5 cm ball over a floor 40 cm thick stands on its top face). The rule was measured in KovaaK's with three test maps. Regression test: a tall spheroid started too low (the importer used twice its radius for every spheroid; KovaaK's starts it the larger of its height and twice its radius above its spawn point). Regression tests: bots that fly or jump move (SYV played as a still ball), health regen, the player's spawn rules and `Cube` walls come through to the world, a brush's own triangles are scaled by `MapScale` (SYW's floor was 8 times too small), the player can be on team 2 and team 0 bots are their opponents (Pasu's bots appeared around the player), and clip brushes are invisible and let shots through while a player who'd spawn in the floor stands on it (Midrange Long Strafes). Rotations match Unreal's `FRotator` matrix (roll turned the wrong way, so VT Pulseshot's room was below the player), a `Ramp` turned to limit the view stops shots just past the limit and nowhere else (DriftTS's crossed the view), four `Concave` corners make a round room that stops shots at its radius (ww5t's wall), and a `WedgeB` floor rises away from its low end (ControlTS's): all on made-up maps. A rotation with `Randomized=false` comes through as taken in turn, and negative regen as a drain (VT Aether's targets were picked at random and never drained); a bot's gravity is 800 units/s² per unit of `Gravity`, as measured in KovaaK's (bots fell with 9.8 m/s² and jumped too low); bot lives, the score for time and the efficiency multipliers (plan K4): `BotMaxLives` is a list with one number per bot slot (regression test: it was read as one number, so `1;1` wasn't refused for lives), one slot with N lives sets a kill limit of N (also beside a helper whose own number is 0), lives on several bots, on some bots and not others, on a helper, on a bot that is only sometimes invincible and in a list that doesn't match the slots are refused as beyond the plan with the setting named, invincible bots (the scenario's or the slot's character's) ignore their lives, `ScorePerTime` and `ScoreMultDamageEfficiency` reach the world, `ScoreMultKillEfficiency` is refused as beyond the plan, and each score combination nobody checked in KovaaK's gets a note while the measured ones stay quiet; `InvincibleBots` comes through (VT Snake Track's bot died); characters start their whole height above where they appear, on both map formats, bots and spawn volumes too; with a head the eye is at the top of the body, and a floor within the step-up height pulls the player down onto it (regression tests: tamTS's player saw from inside the pit and Pasu's from 2 m too low; values measured with test maps in KovaaK's). ### 3. Golden snapshot tests (planned)

Serialize the reports (`TrainingReport`, `ScenarioStats` and the rest) for the fixture set to JSON and compare them with a saved copy, using the `insta` crate. Any change to a metric then shows up as a diff to accept or reject. This catches "I changed the trend window and the dashboard numbers moved" without writing an assertion for every field.

### 4. Robustness tests (planned)

- **Property tests** (`proptest`): random and mangled CSV text never panics the parser; random run timings always give sessions that don't overlap, with active time no larger than session time.
- **Fuzzing** (`cargo-fuzz`, later): the parser over a corpus seeded from the fixtures.

### 5. Database tests

Already covered: a new database migrates to the current schema (version 10, which converts saved ratings to count slips and keeps the old figures in `engine_ratings_v9`), and reopening keeps it. A version 7 database, built in the test from the first seven migrations with one rated run in it, upgrades and keeps that rating as it was: its row has no goal rate, which the conversion needs. A version 8 database, built from the first eight with one planned run in it, upgrades, keeps the run and reads its length back as none. A version 9 database (`a_version_9_database_converts_its_ratings_to_count_slips`) holds rated runs on a lifetime and a target-speed scenario, ratings held at the hardest and at the easiest limit, one held at a limit whose new point falls just inside it, a standard run, a run with no timeline and runs with no text fields. After the upgrade the ratings, their ranges, the start rating and the timeline have moved by the expected amount. An adaptive run's copies of its rating have moved with it: the run's score, and its `Score`, `Rating` and `Start Rating` fields, while `Run Value` stays. A rating held at a limit has stayed there, and its timeline keeps the points at the limit and shifts the others; the one whose point falls inside has moved off the limit. The standard run's score and fields are untouched, the old figures and the old score are in `engine_ratings_v9`, and reopening does not convert twice.

**Rule:** each new migration gets a test that opens a database from the previous version (saved as a fixture) and checks the data survived.

### 6. Real-data check (planned, `#[ignore]`d)

An ignored test that imports your own KovaaK's stats folder into a temporary database and asserts:
- there are zero parse errors
- every run has a score and a run length

Run it before releases with `cargo test -- --ignored`. It catches format changes after game updates, using the largest and most varied dataset available. It stays ignored on CI because CI has no KovaaK's install.

### Manual smoke test (before a release)

1. Install from the release installer on a clean user profile.
2. Launch the app. It should find the stats folder and import existing runs.
3. Play one scenario. The run should appear without restarting the app.
4. Click each screen and check that today, the streak and the latest run look right.
5. Click Rescan. The counts should not change.
6. On Play, start Static Grid and one tracking scenario. Check that mouse sensitivity matches KovaaK's (a full turn should take the same distance), the FPS is well above your monitor's refresh rate, and the run appears on Progress after the trainer closes.

## Known risks to test for

- **Half-written files.** If the watcher reads a file while KovaaK's is still writing it, the file could parse with missing summary fields and be stored for good. Planned fix and test: treat a file without `Score:` and `Challenge Start:` as incomplete, and retry it on the next scan instead of storing it.
- **Daylight saving and time zones.** KovaaK's writes local times with no zone. A run spanning a clock change (e.g. 2 AM on Nov 1, 2026 in the US) gets a length that's off by an hour. Travelling also shifts days. Planned tests: fixtures spanning a DST change, with run length capped at a sane maximum.
- **Format changes after game updates.** The real-data check (layer 6) and tolerant parsing cover this, and new fixtures get added per the fixture policy.
- **Large histories.** Years of training means 10k+ files. Planned: a timing test that imports 10k generated files and builds the snapshot, with a budget (e.g. under 5 s) to catch accidental slow paths.
- **Rust ↔ UI drift.** A renamed field breaks a screen silently. Layers 7 and 8 cover this.

## Coverage

Use `cargo llvm-cov --workspace` from time to time to find untested branches in `aimadapt-core`. There's no hard percentage target; the aim is that every metric shown in the UI is covered by a unit or golden test.
